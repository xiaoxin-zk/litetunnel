# 已知限制登记表

不是所有「看起来像 bug」的东西都能在本仓库根治：有些是协议限制（frps 只支持按名字关闭），
有些是有意的容量边界（队列上限），有些是产品取舍（重置密码不断开已建立的隧道）。

这些东西**必须被登记**，否则每一轮审查都会把它们重新当成 bug 报一遍，真正的缺陷会被淹没。
每条都要回答四件事：**谁处理 / 怎么告警 / 会不会静默丢失 / 是否需要人工介入**。

新增条目时照这个格式填；能自动化检测的，尽量在 `scripts/check-pins.sh` 或 CI 里加门禁。

---

## 1. frps 同名代理关闭竞态

- **现象**：关闭请求返回成功后，同名代理以另一个实例身份重新出现（客户端快速重连）。
- **为什么不能根治**：frps 的 `DELETE /api/v2/proxies/{name}/del` 只认名字，不支持
  「仅当 clientID/lastStartAt 仍是这个值时才删」。条件关闭需要改 frps，不在本仓库范围。
- **已做的缓解**：关闭前用 frps 自己返回的 `clientID/lastStartAt` 比对实例身份；关闭后再核一次，
  身份变化即判定为「疑似误关」，**停止自动重试**并把名单落库（`manual_review` + `suspects`）。
- **谁处理**：运维。看到 `proxy-drain` 的 ALERT 日志或管理端人工待办后，人工核对 frps 中的实例。
- **告警**：`[proxy-drain][ALERT] ... 已转为人工待办`；指标 `ProxyDrainRaceHealth.manual_pending`
  与 `manual_suspects`（落库，跨重启）。
- **静默丢失**：不会。自动重试被主动停掉，记录保留。
- **人工介入**：需要。

## 2. 防火墙待办队列容量与终态

- **现象**：待办上限 `pendingFWLimit`（512）；helper 不可达约 10 分钟（5 次 × 2 分钟）后该端口
  进终态 `exhausted`，不再自动重试。
- **为什么这样设计**：宿主机 helper 长期不可用时，无界重试只会把内存和日志拖垮；收回失败的端口
  需要人看一眼，而不是无限重试。
- **谁处理**：运维。修好 helper 后按 `FailedOps` 清单人工处理（当前没有「重新武装」按钮）。
- **告警**：`[firewall] 端口 %d 连续 %d 次处理失败，已停止自动重试`；管理端 `FailedOps` 列表。
- **静默丢失**：不会丢记录，但**不会自动恢复**。
- **人工介入**：需要。后续可加「重新武装」入口（重置 attempts/exhausted 并 KickFirewall）。

## 3. 断流补偿队列（WAL）的容量与落盘

- **现象**：进程内队列上限 512 条，满了丢最旧的；WAL 落 `/data`（compose 显式指定）。
- **已知边界**：WAL 是「同目录整体重写」，不是追加日志；单文件读取上限 4 MiB。
- **谁处理**：运维关注 `proxy_drain_fallback.dropped` 与 `wal_path`。
- **告警**：丢弃时计数 + 最近 16 个用户 ID；`wal_path` 直接暴露在指标里（路径不可写时队列
  仍照常工作，只在重启后表现为「意图消失」，所以必须能看见路径）。
- **静默丢失**：被淘汰的旧意图会丢（有界队列的必然代价），有指标。
- **人工介入**：`dropped > 0` 时需要。

## 4. 证书扫描预算

- **现象**：单文件 1 MiB、文件数 2000、深度 6、累计读入 32 MiB、证书 500 条、单证书 SAN 100、
  墙钟 2 秒；任一触顶即截断。
- **谁处理**：无（只影响「域名与证书」页的展示完整性）。
- **告警**：截断事实写进 `reason` 与日志，不静默少列。
- **静默丢失**：不丢，但**不完整**。
- **人工介入**：不需要。

## 5. 退出登录 vs 后台同步

- **现象**：同步持门闩期间退出登录最多等 10 秒，等不到就返回「正在同步隧道，请稍后再退出登录」。
  在途那一轮不会被取消。
- **为什么这样设计**：同步中途换账号会让结果写入错误的账号，宁可直接失败。
- **谁处理**：用户重试（网络恢复后一轮同步自然结束）。
- **告警**：界面错误提示。
- **静默丢失**：不会（凭据仍留在磁盘，用户能看到失败原因）。
- **人工介入**：不需要。后续改进：超时时先 `syncCancel()` 再报错。

## 6. 密码重置 / 凭据轮换与已建立隧道

- **现象**：重置密码、轮换 API Key 只失效令牌与会话，服务端**不主动**断开已建立的代理；
  但客户端下一轮同步（≤20 秒）会收到 401，随即自动退出登录并停止本机所有隧道。
- **为什么这样设计**：服务端不杀连接，避免把「改密码」变成一次业务中断；客户端侧必须立刻
  清掉失效凭据，否则界面会停在「已接入」而所有操作都失败——管理员删除用户时尤其明显
  （旧版本不会退出，用户只能自己发现）。轮换 Key 的本意就是让旧客户端失效，自动退出正是期望行为。
- **谁处理**：管理员。只想改密码、不影响在线客户端时，客户端重新接入即可；若怀疑凭据泄露，
  轮换后无需额外操作，旧客户端会在 20 秒内自行退出。
- **告警**：客户端会弹一条「账号已在服务器端失效，已自动退出登录」。
- **静默丢失**：不会。
- **人工介入**：不需要。

## 7. 前端依赖未完全锁定

- **现象**：`client/windows/frontend` 没有提交 `package-lock.json`，`frontend:install` 仍是 `npm install`。
- **影响**：同一份源码在不同时间构建可能解析出不同依赖版本。
- **谁处理**：维护者。需要在有 npm 的环境执行一次 `npm install --package-lock-only` 并提交，
  然后把 `project.json` 的 `frontend:install` 改成 `npm ci`。
- **静默丢失**：不影响运行，只影响可复现性。
- **人工介入**：需要（一次性）。

## 8. 告警生命周期与推送的已知边界

- **事件状态**：同一实例下，同一 `kind` 同时最多一条 `firing`（部分唯一索引按 `(kind, instance)` 兜底）。
  条件自行回落时自动转 `resolved` 并推一条恢复通知；管理员手动解决转 `manual_resolved`，相当于一次
  有审计记录的静默——冷却窗口（30 分钟）内同类问题不再提醒，之后仍在命中才重新开一条。
- **多实例隔离**：告警事件与采样都带实例标识（主机名 + 监听地址，跨重启稳定）。每台实例只用
  自己的样本触发/恢复自己名下的事件，A 的故障不会被 B 的正常样本「恢复」，持续窗口也不会混入
  别人的样本。代价是同一问题在多台实例上会各有一条事件、各推一次通知；面板历史会看到重复项，
  健康分按 `kind` 去重计数。
- **提醒节奏**：一条 `firing` 事件每 30 分钟提醒一次（记在 `last_notified_at`），不新增历史行，
  提醒里带最新读数；恢复通知只发一次。
- **抖动抑制**：自动恢复后 30 分钟内再次命中，视为同一次抖动，**静默重开**原事件：
  不新增历史行，也不立刻补发「又炸了」；若距上次提醒已超过 30 分钟，下一轮按提醒节奏发一条。
  代价是这段时间内状态在面板上会来回变，但不会刷屏。
- **持续判定**：默认 1 个采样窗口命中即触发；设为 N 时要求连续 N 个窗口都超标（回溯
  `lt_metric_samples`，不依赖进程内计数，重启后仍成立）。恢复**不**要求持续，第一个正常窗口
  就收尾。备份超时规则不参与持续判定——它本身以小时计，再等窗口只会白白延后提醒。
- **静默**：全局静默到指定时间（RFC3339，上限一年），期间不新建事件、不推送，恢复状态照常
  维护且不补发恢复通知；截止后问题仍在才重新开一条。静默与「关闭告警」不同：前者仍评估，
  只是不打扰。
- **邮件通道**：与 Webhook 独立。`delivered` 只表示 Webhook 收到 2xx，`mail_queued` 只表示已进发件箱，
  两者都不等于对方服务器已收到；发件箱最终放弃投递时会把 `mail_failed` 回写到事件并**清掉
  `mail_queued`**，页面显示「邮件失败」而不是「已通知」，下一次 30 分钟提醒会重新入队。
  复用发件箱的重试（5 次、指数退避、租约领取），SMTP 抖动不会丢告警。
  限流按**封数**计（多收件人算多封），剩余额度不足时只发给前几个收件人；单实例内能收敛，
  多实例并发仍可能各发各的，超出上限。
- **定时报告**：日报/周报按**服务器本地时区**，统计区间对齐自然日（日报=前一天 00:00~24:00，
  周报=前 7 天），避免流量这类日粒度数据把首尾两个日桶都算进来。发送前用设置表的 CAS 原子认领
  报告期（标记带 10 分钟租约），多实例只有一个会发；一封都没入队时退回认领，进程中途退出则
  租约到期后自动补发。停机错过会在下次启动后补发
  最近一期（不会追溯多期）。收件人复用通知邮箱；部分收件人入队失败只记日志、不单独补发——
  入队失败通常是数据库故障，重试会造成其他人重复收信。摘要只含聚合统计与最近 5 条告警，
  不含用户邮箱等个人信息；统计查询失败时显示「未知」而不是 0。
- **健康分**：算不出来的分项（未采到磁盘、未配置证书 helper、数据库不支持面板备份）标为
  unknown 并从加权中剔除，不给 0 分。证书状态缓存 5 分钟，避免每次打开概览都去问宿主机 helper。
- **推送失败**：先记一条 `delivered=false` 的告警；冷却窗口内的后续采样重试**同一条**记录，
  不新增历史行。没有独立退避队列，接收端长时间不可用时每 5 分钟重试一次。
  恢复通知只在触发通知已送达时发送；它失败后同样在冷却窗口内每轮重试，窗口结束仍未送达
  就停在「恢复未通知」，不再补发。
- **关闭告警**：不再产生新事件，也不再推送；已有事件仍会按条件自动恢复，避免关掉告警后
  面板上一直挂着一条假的「进行中」。
- **出站策略**：拒绝云厂商元数据主机与链路本地/未指定/组播地址（保存时与拨号时各校验一次，
  后者防 DNS rebinding），不跟随 3xx 跳转，也不走 `HTTP(S)_PROXY`（走代理时策略看不到真实目标）。
  私有网段与回环仍然放行，否则自建 ntfy / Gotify 这类最常见的接收端会直接不可用。
- **为什么这样设计**：告警通道本身不可靠时，无界重试会拖住采样循环，还会在接收端恢复后
  一次性灌入大量过期告警。样本不落共享计数器，是因为 5xx 计数在进程内存里，
  跨实例求和反而会产生不存在的「全局错误率」。
- **谁处理**：运维。管理后台「告警与监控」页里「未送达 / 恢复未通知」的记录需要人工核对。
- **告警**：`[alert] Webhook 推送失败（kind）: ...` 日志 + 页面上的通知状态。
- **静默丢失**：不静默——事件一定落库，但**接收端可能没收到**。
- **人工介入**：出现「未送达 / 邮件失败 / 恢复未通知」时需要。多实例部署下每个实例独立采样、
  独立持有事件，阈值判断按实例口径理解。

## 8.1 备份与设置的并发边界

- **备份**：创建/恢复/删除在进程内串行；文件名精确到毫秒并在重名时自增，同一秒连续备份不会
  互相覆盖。多实例同时备份仍可能各写一份（文件名不同），但恢复会覆盖数据库文件，务必只在一台
  实例上操作。
- **设置**：保存时的「读快照 → 合并 → 交叉校验 → 写入」在进程内串行，消除同一实例内并发
  部分更新组合出非法状态的窗口；多实例仍可能交叉，冲突时以最后一次写入为准。
- **网关地址**：面板里的网关主机/端口留空时回落到服务端 `LT_GATEWAY_HOST` / `LT_GATEWAY_PORT`。
  生产环境要求 `LT_GATEWAY_HOST` 非空且不能是回环/`0.0.0.0`——那个地址会原样下发给客户端，
  外部机器会连自己的本机；非生产环境只告警。地址仍为空时客户端页面直接报错，不再下发连不上的地址。
- **节点标识**：持久化在 `lt_settings.node.id`，容器重建、主机名变化都不影响旧告警恢复。
  启动时会把 `instance` 为空的历史告警迁移到当前节点；与当前节点已有 firing 冲突的行保持原样，
  查询条件仍兼容空归属，保证它们能被恢复。
- **报告认领**：报告期标记带 10 分钟租约。进程在「认领成功」与「写入发件箱」之间退出时，
  租约到期后下一轮会自动补发，不会因为标记已推进而永久漏掉这一期。
- **邮件失败重试**：发件箱最终失败会清掉 `mail_queued` 并记 `mail_failed`，下一次 30 分钟提醒
  重新入队；恢复通知单独记录 `resolved_notified / resolved_mail_queued / resolved_mail_failed`，
  入队不再等同于已通知。
- **唯一索引**：`(kind, instance)` 的部分唯一索引是多实例正确性的一部分，创建失败会**阻止启动**，
  而不是只打一行日志继续跑。

## 9. 已知的版本与镜像策略

- **latest 只在发布当前最高版本时移动**（`git tag --sort=-v:refname`）。重新发布旧版本不会覆盖
  latest；若确实需要移动，手工推一次。
- **frp 版本单一来源** `frp-version.txt`，由 `scripts/check-pins.sh` 校验 compose / systemd /
  lt-config 默认值三处一致。
- **端口池三方一致**（`.env.example` / `config.Default()` / `lt-fw.env.example`）同样由
  `check-pins.sh` 门禁，不一致时 CI 直接失败。
